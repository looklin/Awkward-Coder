## 引言

工业数据采集是个「看着简单、做起来处处是坑」的活。

一条中等规模的产线，几百到几千个 PLC 点位，采集周期从 50ms 到 5s 不等；采集到的数据不是只有一个人用——SCADA 要实时显示、历史库要落盘、报警引擎要判阈值、边缘 AI 要喂模型、MES 要拿去做生产统计。**同一份数据，多个消费者，实时性要求还各不相同。**

大多数人的第一反应是上消息中间件，然后陷入纠结：MQTT 轻但吞吐有限，Kafka 稳但延迟高，RabbitMQ 路由灵活但单点吞吐是瓶颈，ZeroMQ 快但没有可靠性。有没有一个方案，天生就是为「**高频、多消费者、确定性、极低延迟**」设计的？

有，它叫 **Aeron**。

Aeron 出身于金融高频交易（HFT）领域——那个对延迟以微秒计的残酷战场。它由 **Martin Thompson**（LMAX Disruptor 的作者、「机械同情 / Mechanical Sympathy」理念的布道者）主导设计。用工业的话说：它是被「最挑剔的实时系统」逼出来的通信基础设施。

问题是：Aeron 到底适不适合工控？和主流 MQTT / ZeroMQ / RabbitMQ / Kafka 比，它的边界在哪里？上位机（SCADA）和 MES 之间又该怎么协同？

本文一次讲透。

## 一、工控数据采集的通信困境

在选型之前，先看清楚问题本身。

### 1.1 典型场景的量级

```
1000 个 tag × 10Hz = 10,000 点/秒
```

这还只是「一个车间」。如果算上振动、电流、温度的波形数据（往往 1kHz 以上采样），

```
8 通道 × 1kHz × 1000 台设备 = 8,000,000 点/秒
```

数据量从「秒级」直接跨到「百万级/秒」。

### 1.2 四类硬约束

| 约束 | 说明 | 被谁逼出来的 |
|------|------|-------------|
| **低延迟** | 联锁保护、闭环控制、实时看板，要求端到端 ms 甚至亚 ms 级 | 控制系统 |
| **多消费者扇出** | 一份数据同时给 SCADA / 历史库 / 报警 / AI / MES | 数据复用 |
| **确定性** | 延迟抖动（jitter）要小，不能偶尔飙到几百 ms | 实时调度 |
| **可靠性** | 断线不丢数据、可重放、可回溯 | 合规与追溯 |

### 1.3 传统方案的错配

| 方案 | 在工控采集里的典型问题 |
|------|------------------------|
| 共享数据库轮询 | 高频下数据库被打爆，延迟从 ms 变成秒 |
| 文件 / 共享内存 | 进程耦合严重，跨机器就歇菜 |
| 单一 MQTT Broker | 单 Broker 在几十万 msg/s 时成为瓶颈 |
| Kafka | 端到端延迟通常在十几 ms 起，抖动大，不适合实时控制链路 |
| ZeroMQ | 快、无依赖，但 PUB/SUB 无可靠性、无背压、丢消息是常态 |

核心矛盾一句话：**高频、多消费者、低抖动、可追溯——很少有方案能同时满足。**

## 二、Aeron 是什么

### 2.1 出身与定位

| 项 | 内容 |
|----|------|
| 作者 | Martin Thompson / Todd Montgomery（Real Logic） |
| 语言 | Java 与 C++ 双实现 |
| 传输 | IPC（同机共享内存）、UDP 单播、**UDP 组播** |
| 定位 | 超低延迟、高吞吐的可靠消息传输 |
| 典型用户 | 交易所、券商、电信、国防、以及部分实时工业场景 |
| .NET 生态 | `Adaptive.Aeron`（NuGet 包） |
| 核心哲学 | Mechanical Sympathy——让软件顺应硬件（CPU 缓存、内存页、无锁） |

### 2.2 核心架构：Media Driver

Aeron 不是一个「你安装了就完事」的 Broker，而是一套**客户端库 + 独立 Media Driver 进程**的组合：

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│  App / Pub  │   │  App / Sub  │   │  App / Sub  │
│ (客户端库)   │   │ (客户端库)   │   │ (客户端库)   │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │  mmap            │                 │
       ▼                  ▼                 ▼
┌──────────────────────────────────────────────────┐
│             Media Driver（独立进程）               │
│  ┌─────────────┐  ┌─────────────┐  ┌───────────┐ │
│  │ Conductor   │  │ Sender      │  │ Receiver  │ │
│  │ (控制面)     │  │ (发送)      │  │ (接收)     │ │
│  └─────────────┘  └─────────────┘  └───────────┘ │
│         Log Buffers / CnC（内存映射文件）           │
└──────────────────────────────────────────────────┘
```

关键点：

- **Media Driver 是传输引擎**，一般是独立进程，客户端通过**内存映射文件（mmap）** 与之共享缓冲区。
- **不经过内核网络栈转发**（同机走 IPC），避免了传统 socket 的多次内存拷贝。
- 传输通道（Channel）用 URI 描述：

```
aeron:ipc                                       # 同机共享内存，最低延迟
aeron:udp?endpoint=192.168.1.10:40456           # UDP 单播
aeron:udp?endpoint=239.1.1.1:40456              # UDP 组播（一份数据扇出多人）
```

### 2.3 为什么快

Aeron 的设计里有几处「机械同情」的巧思：

1. **无锁环形缓冲（Log Buffer + Term Buffer）**：生产者追加、消费者按位置读取，没有锁竞争。
2. **内存映射文件跨进程共享**：同机发布/订阅零拷贝，客户端直接读写共享内存。
3. **背压（Back Pressure）内建**：当消费者跟不上、缓冲区满时，`Offer` 返回失败而不是无限堆积内存——这是很多消息系统缺失的能力。
4. **可配置 Idle Strategy**：`BusySpin`（延迟最低、烧 CPU）→ `Backoff` → `Sleep`，按场景在延迟与 CPU 之间取舍。
5. **UDP 组播扇出**：一次发送，交换机层面复制给多个订阅者，天然契合「一份数据给多个消费者」。

### 2.4 可靠性怎么保证

Aeron 不是「UDP 裸奔」。它在 UDP 之上实现了一套可靠传输协议：

- **NACK 机制**：接收方检测到丢包缺口，主动请求重传（而不是等超时 ACK）。
- **流控与拥塞控制**：内置基于窗口的流控。
- **Aeron Archive**：提供录制与回放（Replay），补齐持久化与历史回溯——**这一点对工控的「数据追溯」至关重要**。
- **Aeron Cluster**：基于 Raft 的复制状态机，用于需要强一致的高可用服务（如 MES 侧的订单态机）。

也就是说：**实时链路用 Aeron 的无损传输，历史链路用 Aeron Archive 落盘回放**，两套能力覆盖了工控的「实时 + 追溯」。

## 三、Aeron 在工控数据采集中的落地

### 3.1 参考拓扑

```
  ┌────────┐ ┌────────┐ ┌────────┐
  │ PLC#1  │ │ PLC#2  │ │ ...N   │  ← Modbus / OPC UA
  └───┬────┘ └───┬────┘ └───┬────┘
      │          │          │
      ▼          ▼          ▼
  ┌──────────────────────────────┐
  │   边缘采集网关 (Edge Gateway)   │
  │  协议解析 → 归一化 → 打时间戳     │
  │  内部分发：aeron:ipc            │
  └──────────────┬───────────────┘
                 │ aeron:udp?endpoint=239.1.1.1:40456
                 │ （UDP 组播，一次发送多点接收）
      ┌──────────┼──────────┬───────────┐
      ▼          ▼          ▼           ▼
  ┌───────┐ ┌────────┐ ┌────────┐ ┌──────────┐
  │ SCADA │ │ 历史库  │ │ 报警引擎│ │ 边缘 AI   │
  │ 实时画面│ │ Archive│ │ 阈值判断│ │ 振动分析  │
  └───────┘ └────────┘ └────────┘ └──────────┘
```

这个拓扑的精妙之处：**网关只用组播发一份数据**，SCADA、历史库、报警、AI 各自订阅，互不干扰。任何一路消费者卡住或重启，都不会影响其他消费者，也不拖慢采集节拍。这正是 MQTT Broker 与 Kafka 在「单点扇出」上难以在低延迟下做到的。

### 3.2 采集侧最小示例（.NET / Adaptive.Aeron）

先说部署前提：需要先启动 Media Driver（Java 或 C++ 版本均可），再运行你的应用。

```bash
# 启动 Media Driver（示意，实际按发行包路径）
java -cp aeron-all.jar io.aeron.driver.MediaDriver
```

```bash
dotnet add package Adaptive.Aeron
```

**发布端（采集网关）：**

```csharp
using Adaptive.Aeron;
using Adaptive.Agrona.Concurrent;

// 连接 Media Driver
using var aeron = Aeron.Connect();

// 一组采集点位的扇出通道（UDP 组播）
var channel  = "aeron:udp?endpoint=239.1.1.1:40456";
const int StreamId = 1001;

using var publication = aeron.AddPublication(channel, StreamId);

// 轮询多个 PLC 后，把归一化后的数据帧发布出去
while (running)
{
    var frame = ReadPlcs();          // 你的采集逻辑，产出 byte[]
    long result = publication.Offer(frame, 0, frame.Length);

    if (result < 0)
    {
        // 负值表示背压：消费者跟不上，缓冲区满。
        // 工业场景里这通常意味着要降采样或扩消费者，而不是死等。
        HandleBackPressure(result);
    }
}
```

**订阅端（例如 SCADA 实时刷新）：**

```csharp
using var aeron = Aeron.Connect();
using var subscription = aeron.AddSubscription(
    "aeron:udp?endpoint=239.1.1.1:40456", 1001);

var assembler = new FragmentAssembler(OnFragment);

while (running)
{
    // 一次最多 poll 10 个 fragment，无数据时按 IdleStrategy 退避
    int fragments = subscription.Poll(assembler.OnFragment, 10);
    idleStrategy.Idle(fragments);
}

void OnFragment(UnsafeBuffer buffer, int offset, int length, Header header)
{
    // 零拷贝解析：直接读取共享缓冲区
    var sample = Parse(buffer, offset, length);
    ui.Update(sample);
}
```

### 3.3 落地时必须踩清的坑

| 坑 | 现象 | 对策 |
|----|------|------|
| **组播网络配置** | 订阅者收不到数据 | 交换机开启 IGMP Snooping；TTL、网段、网卡 interface 参数要对 |
| **Media Driver 独立进程** | 忘了启动，客户端连不上 | 部署脚本里显式拉起，纳入服务托管/看门狗 |
| **BusySpin 烧 CPU** | 服务器 CPU 100% | 非极致实时场景改用 `Backoff`/`Sleep` 空闲策略 |
| **大帧与 MTU** | 大报文分片、丢包率上升 | 开启 Jumbo Frame（9000），或缩小消息粒度 |
| **跨网段/跨机房** | 组播过不了三层 | 组播仅限同一二层局域网；跨网段改用单播或 Kafka 补齐 |
| **Java 依赖** | 想纯 .NET 却要装 JRE | 用 C++ 版 Media Driver，或接受独立运行时 |

> 一句话经验：**Aeron 的适用域是「同一局域网内的高频扇出」**。跨三层、跨地域、需要海量持久化历史的场景，交给 Kafka 更省心。

## 四、五大消息方案横向对比

### 4.1 定位速览

| 方案 | 类型 | 传输 | 持久化 | 核心哲学 |
|------|------|------|:---:|---------|
| **Aeron** | 库 + Media Driver | IPC / UDP 单播 / **UDP 组播** | 需 Archive | 机械同情、极低延迟、多播扇出 |
| **MQTT** | Broker（Mosquitto/EMQX） | TCP | ⚠️ 视 Broker | 轻量、省电、弱网、海量设备 |
| **ZeroMQ/NetMQ** | 纯库（无中间件） | TCP / IPC | ❌ | 无 Broker 的进程间通信骨架 |
| **RabbitMQ** | Broker | AMQP (TCP) | ✅ | 可靠路由、灵活交换 |
| **Kafka** | 分布式流平台 | TCP | ✅ | 不可变日志、高吞吐、可回溯 |

### 4.2 架构模型差异

**Aeron**——「总线式多播」：

```
Publisher ──► [Media Driver / 组播总线] ──┬──► Sub A
                                        ├──► Sub B
                                        └──► Sub C
                        一份数据，网络层复制扇出
```

**MQTT**——「星型 Broker」：

```
Device ──► [Broker] ──► Subscriber(s)
              │
         所有流量过 Broker，Broker 是中心也是上限
```

**ZeroMQ**——「无中心，Socket 直连」：

```
Publisher ──PUB──┬──► SUB
                 └──► SUB
         无服务器，模式即拓扑；无可靠性保证
```

**RabbitMQ**——「交换器路由」：

```
Pub ──► [Exchange] ──Binding──► [Queue] ──► Consumer
```

**Kafka**——「分区日志」：

```
Topic ──┬─ Partition 0 [0,1,2,...N]  ← 只追加、不删除
        └─ Partition 1 [0,1,2,...N]
        Consumer 按 Offset 定位，可回溯
```

### 4.3 性能对比（量级参考）

> 数值为常见部署下的**量级**，随硬件、消息大小、网络、持久化配置浮动很大，仅供选型参考，务必以自测为准。

| 维度 | Aeron | MQTT(EMQX) | ZeroMQ | RabbitMQ | Kafka |
|------|:---:|:---:|:---:|:---:|:---:|
| 端到端延迟 | **~μs 级** | ~ms | ~μs 级 | ~ms | ~10ms+ |
| 单节点吞吐 | **百万~千万/秒** | 十万~百万/秒 | 百万+/秒 | 万~十万/秒 | **百万~千万/秒** |
| 延迟抖动 | **极低** | 中 | 低 | 中 | 较高 |
| 扇出方式 | **UDP 组播一次到位** | Broker 复制 | 无中心复制 | Exchange 复制 | 分区消费组 |
| 背压 | ✅ 内建 | ⚠️ 弱 | ❌ 无 | ✅ | ✅ |
| 持久化 | Archive | Broker 可选 | ❌ | ✅ | ✅ 强 |
| 消费回溯 | ✅ (Replay) | ❌ | ❌ | ⚠️ 有限 | ✅ 强 |

### 4.4 可靠性与运维

| 维度 | Aeron | MQTT | ZeroMQ | RabbitMQ | Kafka |
|------|:---:|:---:|:---:|:---:|:---:|
| 投递语义 | 至少一次 / 可靠传输 | QoS 0/1/2 | 尽力而为 | 至少一次 | 至少一次 / 精确一次 |
| 断线续传 | ⚠️ 需自建 | ⚠️ 靠会话 | ❌ | ✅ | ✅ |
| 历史回溯 | ✅ Archive | ❌ | ❌ | ⚠️ | ✅ |
| 部署复杂度 | 中（需 Media Driver） | 低 | **最低** | 低 | 高 |
| 运维复杂度 | 中 | 低 | 低 | 中 | **高** |
| 生态成熟度 | ⚠️ 偏金融/小众 | ✅ 极成熟 | ✅ 成熟 | ✅ 成熟 | ✅ 极成熟 |

### 4.5 选型决策树

```
你的数据要在同一局域网内高频扇出给多个消费者？
├─ 是 → 延迟要求是 μs 级、且消费者多？
│        ├─ 是 → Aeron（UDP 组播）★
│        └─ 否 → ZeroMQ PUB/SUB（简单够用）
├─ 否 → 需要海量持久化 / 回溯 / 流处理？
│        ├─ 是 → Kafka ★
│        └─ 否 → 需要复杂路由 / 可靠业务消息？
│                 ├─ 是 → RabbitMQ ★
│                 └─ 否 → 设备侧 / 弱网 / 云端上行？
│                          └─ 是 → MQTT ★
```

## 五、工厂上位机与 MES 的通信协同方案

### 5.1 先理清层次（ISA-95）

工业信息化天然是分层的，通信方案必须「对号入座」：

```
Level 4  企业层  ERP / 集团 BI
             ▲
Level 3  MES / 制造运营层（工单、追溯、质量、OEE）
             ▲
Level 2  监控层  SCADA / HMI / 上位机
             ▲
Level 1  控制层  PLC / DCS / 运动控制器
             ▲
Level 0  现场层  传感器 / 执行器 / 仪表
```

铁律：**越靠下，实时性越强、数据量越碎；越靠上，越重业务语义、越重可靠性。**

### 5.2 分层通信方案（推荐组合）

| 层次 | 主要需求 | 推荐方案 | 理由 |
|------|---------|---------|------|
| L0–L1 现场/控制 | 硬实时、确定性 | **现场总线 / PROFINET / EtherCAT** | 由控制系统厂商生态决定 |
| L1–L2 设备接入 | 语义化读写 | **OPC UA**（或 Modbus + 网关） | 标准信息模型、类型安全 |
| L2 内部分发 | 高频、多消费者扇出 | **Aeron（UDP 组播 / IPC）** | μs 级、一次发送多点接收 |
| L2–L3 上行 | 生产数据落库、追溯 | **Kafka** | 高吞吐、可回溯、解耦 |
| L2–L3 业务消息 | 工单、指令、确认 | **RabbitMQ** | 可靠路由、请求-应答、重试 |
| 远程 / IIoT | 弱网、设备上行、云 | **MQTT** | 轻量、断线重连、省带宽 |
| 进程内 / 同机 | 组件间解耦 | **ZeroMQ / IPC** | 零依赖、最简单 |

### 5.3 上位机（SCADA）↔ MES 的三种协同模式

**模式 A：直连（轻量、快，但耦合）**

```
SCADA ──OPC UA / REST / DB──► MES
```

- 适合：单车间、数据量小、MES 与 SCADA 同厂同网。
- 缺点：接口点对点，N 个上位机 × M 个 MES 模块 → 接口爆炸；SCADA 升级易波及 MES。

**模式 B：消息中间件解耦（推荐主流）**

```
SCADA ──┐                     ┌──► MES 生产统计
        ├─► Kafka（数据骨干）──┼──► MES 质量追溯
历史库 ──┘                     ├──► MES OEE 分析
                              └──► BI / 数据湖
```

- SCADA 只负责「把发生的事发出来」，MES 各模块各自订阅。
- 生产者与消费者彻底解耦，新增消费者不影响 SCADA。
- Kafka 的日志特性天然满足「可回溯、可补数」。

**模式 C：实时 + 骨干混合（本文推荐的完整形态）**

```
 L2 实时域                      L3 业务域
┌─────────────┐               ┌───────────────┐
│ Aeron 组播   │               │  Kafka 骨干    │
│ (μs 级扇出)  │               │ (持久化/回溯)   │
└──────┬──────┘               └───────┬───────┘
       │ SCADA/HMI/报警/AI 订阅实时流    │ MES/BI 订阅业务流
       │                              │
       └──── 采集网关（双写）───────────┘
             实时走 Aeron，业务事件走 Kafka
```

**核心思想：实时域用 Aeron 保证「快」，业务域用 Kafka 保证「稳」，网关做双写或桥接。**

- 实时域（Aeron）：画面刷新、联锁报警、闭环下发——要的是**低延迟低抖动**。
- 业务域（Kafka）：工单完工、质量判定、追溯事件——要的是**不丢、可查、可重放**。
- 两者用**网关桥接**：网关订阅/发布 Aeron 实时流，同时把聚合后的业务事件写入 Kafka。这样上层 MES 完全不用感知 Aeron 的存在。

### 5.4 消息契约与语义建模（易被忽视，但决定成败）

工业系统的通信难点，往往不在「传得快不快」，而在「传的内容有没有共识」。

- **统一时间基准**：所有数据带 UTC 时间戳 + 采集源 ID，跨设备对齐用 NTP/PTP。**时序错了，追溯全是错的。**
- **统一对象模型**：以 ISA-95 的设备/工单/物料层级组织 payload，避免「同一台设备三个系统三种命名」。
- **序列化选型**：
  - Aeron 链路推荐 **SBE**（Simple Binary Encoding，低延迟的原生搭档）或 Protobuf。
  - 业务域（Kafka/MQTT）用 **Protobuf / JSON**，可读性与兼容性优先。
- **Schema 版本管理**：字段只增不删、兼容演进，注册中心统一维护，避免上下游「静默失联」。

### 5.5 一致性与高可用

| 问题 | 方案 |
|------|------|
| 采集断线丢数 | 网关本地缓存 + 断点续传（Archive/Kafka offset） |
| 跨系统数据不一致 | 以 SCADA/网关为单一数据源，MES 只读不写实时流 |
| 单点故障 | MES 侧用 RabbitMQ Quorum Queue / Kafka 多副本；实时域用多播接收端各自容错 |
| 指令下发可靠性 | 业务指令走 RabbitMQ（可靠确认），不混入实时流 |
| 时钟漂移 | 全厂 PTP 对时，关键事件双时间戳（设备时间 + 网关接收时间） |

### 5.6 落地清单（Checklist）

- [ ] 明确每条数据链路的**实时性等级**（控制级 / 监控级 / 业务级）
- [ ] 现场/控制层交给既有现场总线与控制器生态，不强行替代
- [ ] L1–L2 用 OPC UA 统一语义，网关做协议归一化
- [ ] L2 内部高频扇出评估 Aeron（**先做 PoC 验证组播网络**）
- [ ] L2–L3 上行用 Kafka 做数据骨干，保证持久化与回溯
- [ ] 业务指令与工单走 RabbitMQ，与数据流分离
- [ ] 远程/云端接入用 MQTT，不与内网实时域混用
- [ ] 全链路统一时间戳与对象模型，Schema 做版本管理
- [ ] 部署脚本显式拉起 Media Driver，纳入服务托管与看门狗
- [ ] 压测：**用自己的真实数据、真实网络**跑，不看厂商标称值

## 六、选型建议与总结

### 6.1 一句话选型

| 场景 | 首选 |
|------|------|
| 同局域网、高频、多消费者、μs 级扇出 | **Aeron** |
| 设备侧 / 弱网 / 云端上行 / 海量终端 | **MQTT** |
| 进程间通信 / 不想引入中间件 | **ZeroMQ / NetMQ** |
| 复杂路由 / 可靠业务消息 / 请求-应答 | **RabbitMQ** |
| 数据骨干 / 持久化 / 回溯 / 流处理 | **Kafka** |

### 6.2 关于 Aeron 的理性判断

Aeron 不是银弹，它的边界很清晰：

**它擅长的：**
- 同一局域网内的高频数据扇出（UDP 组播一次到位）
- 同机进程间的零拷贝通信（IPC）
- 对延迟抖动极度敏感的实时链路

**它不擅长的：**
- 跨三层 / 跨地域（组播过不去）
- 开箱即用的持久化历史（需自行接 Archive）
- 小团队快速上手（生态偏小众，Media Driver 需独立运维）

> 好消息是，**Aeron 和 Kafka 并不冲突**——实时域用它，业务域用 Kafka，各司其职，这正是工控场景该有的组合拳。

### 6.3 最终架构心法

工控通信选型的本质，不是「选最强的那个」，而是**让每一层用最合适的方案**：

- **越往下，追求确定性与低延迟** → 现场总线、OPC UA、Aeron
- **越往上，追求可靠性与语义** → Kafka、RabbitMQ、MQTT

一位老工程师说过一句话，用在这里很贴切：

> **不要用一种技术解决所有问题，要用一堆合适的技术解决各自的问题。**

工业系统的稳定，从来不是靠某个「万能中间件」撑起来的，而是靠**清晰的分层、明确的边界、统一的语义**——以及，被真实压测验证过的每一个环节。
